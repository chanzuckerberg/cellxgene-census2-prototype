# Spike: a typed filter builder for `obs`, over per-dataset and consolidated stores

This file records the filter builder spike on the branch `spike/consolidation-filters`, which is
stacked on the store consolidation spike (`spike/store-compaction`, `spikes/store-consolidation.md`).
The branch is a running-code reference and is not intended to merge in its current form. No
decision in it is final. The draft pull request gives the summary; this file holds the details.

The spike asks one question: can one caller filter apply to the `obs` of many AnnData-Zarr stores,
the same way on each store, with no `obs` Parquet fragments, no Iceberg, and no DuckDB? The answer
here is a typed Python builder with pandas names. A query resolves the filter once against the
catalog, binds it to the codes of each candidate store, and evaluates it with pyarrow compute
expressions. The cell keys equal those of the DuckDB path of the SQL spike (`spike/obs-duckdb`) for
all 29 queries of the cross-check.

## 1. What the spike built

- `census2_sdk.obs_filter`: the column classes, the expression tree, `repr`, the normal form, and
  the label tests.
- `census2_sdk.obs_columns`: the typed `obs` of an organism, generated by
  `tools/generate_obs_columns.py` from the writer's `store_format.OBS_COLUMNS`.
- `census2_sdk.obs_plan`: the resolution of a filter, the label check, and the catalog test.
- `census2_sdk.obs_arrow`: the read of `obs` columns from Zarr, the bind of a filter to one store,
  the compile to a `pyarrow.compute.Expression`, the evaluation, and the result columns.
- `Census.homo_sapiens` and `Census.mus_musculus` (`Organism`): `get_anndata`, `get_obs`, `count`,
  `count_by`, and `plan`. `Census.get_anndata(organism, mapping)` stays as it was.
- `catalog.open_store(uri, lean=True)`: `zarr_format=3` and one obstore client for each bucket.
  The builder path always opens a store this way.
- Benchmark tools: the `builder` shape of `bench.run` and its named queries (`bench/filters.py`),
  `bench/bind.py` (bind and evaluation milliseconds for each store, against `read_elem(obs)`),
  `harness/filter_language_builder.py` (the corpus and the probes in builder form), and the scripts
  in `spikes/consolidation-filters/`: the cross-check of the cell keys, the dictionary measure, the
  test store with nulls, and the summary of the measures.
- 146 new tests (308 in the SDK), mypy `--strict` with the error code `deprecated` on.

The writer does not change, and the spike needs no ingest. It reads the round-2 stores of the
consolidation spike (103 per-dataset stores, 5 consolidated stores, and their catalogs) and the
round-2 stores and catalog of the Iceberg spike, which the DuckDB spike queried.

## 2. The builder

```python
hs = census.homo_sapiens
obs = hs.obs
f = obs.tissue_general.isin(["lung", "blood"]) & obs.is_primary_data
f &= ~obs.cell_type.str.contains("macrophage", case=False)
f &= obs.disease.has_any(["COVID-19"]) | (obs.nnz >= 500)
repr(f)
# (obs.tissue_general.isin(['blood', 'lung']) & obs.is_primary_data
#  & ~obs.cell_type.str.contains('macrophage', case=False))
#  & (obs.disease.has_any(['COVID-19']) | (obs.nnz >= 500))
adata = hs.get_anndata(f, layers=["normalized"], max_workers=8)
frame = hs.get_obs(f, columns=["cell_type", "donor_id"])
counts = hs.count_by("donor_id", f)
```

| Column class | Columns | Operators |
|---|---|---|
| `CategoryColumn` | the 20 label columns and `dataset_id` | `==`, `!=`, `isin`, `.str.startswith`, `.endswith`, `.contains`, `.match`, `.fullmatch` |
| `MultiValueColumn` | `disease`, `disease_ontology_term_id` | `has_any([...])`, `has_all([...])` only |
| `BoolColumn` | `is_primary_data` | the column as a filter, `~`, `==` a bool |
| `IntColumn`, `FloatColumn` | `nnz`, `n_measured_vars`; `raw_sum`, `raw_mean_nnz`, `raw_variance_nnz` | `<`, `<=`, `>`, `>=`, `==`, `!=`, `between` |
| `StringColumn` | `observation_joinid` | `==`, `!=`, `isin` |
| `AnyColumn` | `obs["name"]`, for a column that the static schema does not name | all of the above; checked at query time |

Every column also has `isna()` and `notna()`.

### 2.1 The decisions, for discussion

The operator made these decisions for the spike. Each is open for discussion.

1. **pandas names.** `isin`, `between`, `isna` and `notna`, `.str` methods, the comparisons, and
   `&`, `|`, `~`. The spike adds `.str.endswith`, `.contains` (with `case` and `regex`),
   `.match`, and `.fullmatch`, with the arguments of pandas.
2. **One namespace for each organism.** `census.homo_sapiens.obs.<column>` and
   `census.homo_sapiens.get_anndata(obs_filter=...)`. A filter remembers its organism; a filter of
   two organisms, or of another organism than the query, raises `FilterError`. The two organisms
   share one generated class today.
3. **Typed columns, statically checked.** mypy `--strict` checks the operators, and the tests use
   `assert_type`. `==`, `!=`, and `isin` on a multi-valued column are type errors and raise
   `TypeError` at run time with a hint. `__bool__` raises, so `and` and `or` give a hint to use
   `&` and `|`. `repr` is for display; the SDK parses no text form of a filter.
4. **No ontology closure.** A caller passes `isin([...])` of the terms.
5. **The null rule of a pandas mask.** A null equals nothing. Each term is two-valued (a null gives
   False) before `~`, `&`, and `|` combine it, so `~(x == "a")` keeps the null rows. `isna()` and
   `notna()` test the null itself.
6. **Zarr-only engines.** The builder compiles to the catalog value-set test and to pyarrow compute
   expressions over `obs` read from the stores.
7. **No R front end** in this spike.

### 2.2 How mypy sees a wrong operator

mypy cannot make `==` itself an error by its argument type: when the left operand refuses the
argument, mypy falls back to `object.__eq__` and gives `bool`. The builder therefore marks each
refused operator with `@deprecated` (PEP 702) and gives it the return type `Refused`. With the error
code `deprecated` on (this package's `pyproject.toml` turns it on), mypy reports
`obs.disease == "COVID-19"` on that line. Without it, mypy reports the misuse where the result is
used, because `Refused` is not a filter. The same applies to `obs.tissue == 3` and
`obs.nnz == "3"`. The tests prove each refusal with `# type: ignore[deprecated]`, which mypy would
report as an unused ignore if it did not see the misuse. The marker is a type-checker mechanism and
says nothing about a deprecation. pyright reports `deprecated` as a hint by default.

## 3. Resolve once, bind for each store

```text
filter ──resolve (once)──> plan: tree, columns, candidates with a residual each
                               │
            ┌──────────────────┴───────────────────┐
     per-dataset store                     consolidated store
     (all rows)                            (adjacent candidate members, one read)
            │                                      │
     read the residual's columns (codes and values, no strings)
     bind: label terms by category → boolean columns; numeric terms stay
     evaluate: one pyarrow Expression, Acero project → kept rows
            │
     count | count_by | get_obs | get_anndata (the other columns and X for the kept rows only)
```

### 3.1 The resolution

`Organism.plan(f)` (`obs_plan.resolve`) runs once for each query:

1. **Check.** The organism of the filter must be the organism of the query. A column of the
   static schema takes the operators of its kind, also through `obs["name"]`: for example,
   `obs["disease"] == "normal"` raises `FilterError` with the hint to use `has_any`. A column that
   the static schema does not name waits for the stores.
2. **Labels.** Each label of `==`, `isin`, `has_any`, and `has_all` on a column with a catalog
   value set is checked against the union of the value sets of the organism's catalog rows. When
   every label of a term is unknown (or one label of `has_all`), the term can match no cell, and
   the query raises `FilterError` with the nearest known labels (`difflib`, and the same label in
   another case first): `tissue has no value 'lugn' in any dataset of the catalog, so obs.tissue ==
   'lugn' matches no cell. 'lugn': did you mean 'lung'?`. An unknown label with a near known label,
   next to known labels, gives a warning. An unknown label without a near label passes in silence,
   so an `isin` of ontology terms that the release does not hold still works.
3. **Normal form.** `~` moves to the terms (De Morgan's laws hold, because every term is
   two-valued), `between` becomes two comparisons, `x != v` becomes `~(x == v)`, nested `&` and `|`
   flatten, constants fold, and terms on one label column merge: `==` and `isin` under `|` become
   one `isin`, their negations under `&` one negated `isin`, `has_any` under `|` one `has_any`, and
   `has_all` under `&` one `has_all`. The merge makes the catalog test more exact.
4. **The catalog test.** See 3.2.

The result is a `Plan`: the normalized tree, the set of columns, and the candidates, each with its
catalog row and its residual filter. `repr(plan)` gives the counts, for example
`<Plan homo_sapiens: obs.tissue_general.isin(['brain', 'lung']); 44 of 103 datasets, 32 whole>`.

### 3.2 The catalog test

The test gives one of three answers for each term and each catalog row: every cell of the dataset
matches (`ALL`), no cell matches (`NONE`), or the row cannot tell (`SOME`).

- A label term on a column with a value set: `NONE` when no value of the set passes the term,
  `ALL` when every value passes and the column holds no null, else `SOME`. A multi-valued column
  tests the members of each joined value. `.str` terms test each value with the same function as
  the stores (`obs_filter.label_test`, Python's `str` and `re`), so the catalog and the stores
  cannot disagree on a value.
- `dataset_id`: exact, from the row's identity.
- `is_primary_data`: the row records `all_true`, `all_false`, or `mixed`, which give `ALL`, `NONE`,
  and `SOME`.
- `isna()` on a column with a value set: `NONE`.
- A numeric term, a column that the row does not record, and a column of `obs["name"]` that the
  schema does not name: `SOME`.

`&` gives `NONE` when one child gives `NONE`, and `ALL` when all give `ALL`; `|` the reverse; `~`
swaps `ALL` and `NONE`. A row whose answer is `NONE` is excluded. The test is exact for one term on
a recorded column, and conservative for several terms: `(tissue == "lung") & (cell_type == "x")`
keeps a dataset with lung cells and `x` cells in other tissues.

**The null rule at the catalog.** A term is `ALL` only when no cell can hold a null, so `~` gives
`NONE` only when the catalog can prove that the dataset has no null in that column. The catalog
records no null today. The spike takes the store format's rule instead: no column of `OBS_COLUMNS`
holds a null, and the writer refuses one in each column that it copies (`tissue_general` comes from
`tissue`, which holds none). The catalog builder drops nulls from a value set, so a store of another
writer with nulls in an indexed column would give a wrong `NONE` for a negated term. A store format
that admits nulls needs the catalog to record them, for example one list of the indexed columns that
hold a null in each row. A column that the catalog does not record proves nothing, so a negated term
on it, or on `obs["name"]`, keeps every dataset.

**Residuals.** The `ALL` and `NONE` parts of the tree become constants, and the tree simplifies.
The residual of a candidate is the filter of its cells. A residual of `True` means every cell
matches, so the store reads no column to find them, and `count` takes the number from the catalog
row with no store open. Of the 44 candidates of `tissue_general in ['brain', 'lung']`, 32 are
whole; of the 17 of `tissue_general_ontology_term_id == 'UBERON:0002048'`, 7 are. `dataset_id`
terms are always whole or excluded.

### 3.3 Reads

`_units` groups the candidates by their serving store: a per-dataset store reads all of its rows;
the candidate members of a consolidated store that are adjacent in its rows (each starts where the
one before stops) read as one range. The members of a run read the union of the columns of their
residuals once, and each member then evaluates its own residual on its part of the data (a slice,
without a copy). Opens and reads use the thread pool of `max_workers`, and each read reads its
columns with up to 8 threads of its own, as `main` does.

A referenced column that a store lacks follows the rule of `main`'s `_mask`: that store gives no
cells. The query gives one warning for each such column, with the count of stores. When no store
read holds a column of `obs["name"]`, the query raises `FilterError` with the nearest column names
(`no store holds the obs column 'author_lable'; did you mean 'author_label'?`).

A query reads in two rounds. The first reads only the residual's columns for the rows of the read.
The second reads, for the kept rows only, the other columns of the result and the cell key. A read
that keeps no cell reads nothing more, which is where a catalog false positive costs least.
`count` and `count_by` have no second round. `get_anndata` then reads `X` for the kept rows with
`main`'s `_rows`, and calculates the normalized layer with `main`'s code.

## 4. The Arrow table from Zarr

`obs_arrow.read_column` reads one column for a row range directly with zarr, by anndata's on-disk
format. It checks `encoding-type` and `encoding-version`:

| Encoding | Version | Read | Arrow |
|---|---|---|---|
| `categorical` | 0.2.0 | `codes[start:stop]`, and `categories` once for each store | `DictionaryArray.from_arrays`: the codes without a copy; a code of -1 becomes a null in the validity bitmap (one pass, only when a code is -1) |
| `array` (bool) | 0.2.0 | `values[start:stop]` | one pass that packs the bits |
| `array` (int64, float64) | 0.2.0 | `values[start:stop]` | the NumPy buffer without a copy |
| `string-array` | 0.2.0 | `values[start:stop]` | a string array (one string for each cell) |
| `nullable-integer`, `nullable-boolean`, `nullable-string-array` | 0.1.0 | `values` and `mask` | the values with `mask` as nulls |
| any other | | `anndata.io.read_elem`, then the rows | as above |

The tests check that the indices and a numeric column wrap the NumPy buffers without a copy (the
same address). The filter reads neither `observation_joinid` nor the `obs` index. The categories of
a consolidated store's column are read once for all of its members (`CategoryCache`).

The result `obs` is built for the kept rows only. A categorical column takes the codes of the kept
rows, keeps only the categories that they use (one `bincount`), and becomes
`pd.Categorical.from_codes(..., validate=False)`; the codes come from the store, so pandas does not
check them again. A numeric or boolean column takes the kept values. The cell key and any other
encoding read the kept rows only with `main`'s reader (`obs_arrow.read_rows`), so their dtypes are
those of `read_elem`. `get_obs` joins the cell key `<dataset_id>_<observation_joinid>` in Arrow
(`binary_join_element_wise`), not one Python string at a time.

### 4.1 Bind and evaluate

`obs_arrow.bind` replaces each term of the residual:

- **A label term** (`==`, `isin`, `.str`, `has_any`, `has_all`) on a categorical column: the term
  is tested once for each category, with `label_test`, to a lookup table of booleans; the cells take
  `table[codes]`, with a False at the end for the code -1. A string column is dictionary-encoded
  first. This is the store-local bind of `has_any` and `has_all`: an `isin` over this store's
  joined values that hold any (or all) of the wanted members, with no regular expression and with a
  cost for each category, not for each cell. A term that no category passes becomes False; a term
  that every category passes, on a column without a null code, becomes True. The result is a
  boolean column of the bound table (`Field`).
- **A numeric or boolean term** stays a term on its Arrow column: `pc.field("nnz") >= 500`.
- **`isna()`**: the code -1, the mask, or NaN, as a boolean column.

The bound tree normalizes again, so a store can fold the whole filter to a constant. Otherwise
`compile_expression` gives one `pyarrow.compute.Expression`: `pc.field` for each boolean column,
the comparisons for the numeric terms, and `&`, `|`, `~`. A term on a column with nulls is wrapped
in `coalesce(term, false)`, which gives the pandas rule; a column without nulls needs no wrap.
`evaluate` projects the expression over the bound table with an Acero `project` node, with
`use_threads=False`, and the positions of the True values are the kept rows. A tree of one boolean
column skips Acero. A reference form, `to_expression`, compiles the same tree for pyarrow on
decoded strings; a property test compares the two on random trees with null codes and nullable
values.

## 5. Does pyarrow evaluate a dictionary array over its dictionary?

No, not in pyarrow 26.0.1. `equal` and `is_in` on a dictionary array decode it to one string for
each cell and then compare. `starts_with` and the other string functions have no kernel for a
dictionary array and raise `ArrowNotImplementedError`. An expression through `Table.filter` or an
Acero `project` node does the same. One thread (`pyarrow.set_cpu_count(1)`), 2 million cells,
best of 7, on the laptop (`spikes/consolidation-filters/dictionary.py`,
`results/consolidation_filters/dictionary-laptop.jsonl`):

| Measure | 300 categories, ms | 30,000 categories, ms |
|---|---|---|
| decode | 12.9 | 13.1 |
| equal, dictionary | 16.9 | 17.2 |
| equal, strings | 4.1 | 4.0 |
| is_in, dictionary | 26.9 | 27.0 |
| is_in, strings | 14.0 | 13.8 |
| starts_with, strings | 4.4 | 12.0 |
| Table.filter(==), dictionary | 17.9 | 18.1 |
| Table.filter(==), strings | 5.1 | 4.9 |
| Acero project(==), dictionary | 17.6 | 17.5 |
| Acero project(isin), dictionary | 27.5 | 27.4 |
| by codes: is_in on the dictionary, take | 5.0 | 5.1 |
| by codes: NumPy lookup table | 2.3 | 2.3 |

`equal` on the dictionary array costs about the decode plus `equal` on the strings, and `is_in`
the decode plus `is_in` on the strings. The evaluation by codes is 7 times faster for `==` and 12
times for `isin`, and the number of categories does not change it. Thus `bind` evaluates each label
term on the categories with Python and maps the result by the codes with NumPy, as `main`'s `_mask`
does, and gives pyarrow only boolean columns and numeric terms. Two smaller findings:
`Table.filter(expression)` takes every column of the table and costs 9 times the evaluation at 1
million rows, so `evaluate` projects a boolean mask instead (1.9 ms against 1.5 ms for the bare
compute functions); and pyarrow's regular expressions are RE2, not Python's `re`, so the label
tests use Python for both the catalog and the stores.

## 6. The cross-check against the DuckDB spike

The DuckDB path ran from a separate checkout of `spike/obs-duckdb` with its own environment
(`duckdb_keys.py`), over the round-2 fragments and catalog of the Iceberg spike. The builder ran
over the stores of the same catalog (`builder_keys.py`). Each script records the number of cells
and a SHA-256 of the sorted cell keys `(dataset_id, observation_joinid)`
(`results/consolidation_filters/crosscheck-*.json`, `*-keys-*.jsonl`).

- **29 of 29 queries give the same cell keys**: the shared set, (a) to (g) and the counts, the
  probes of the SQL spike that have a builder form, and the new queries (`|` across columns,
  `has_any`, `has_all`, numeric ranges, `between`, `NOT IN`, patterns, `isna`). The sets go from 0
  to 13,316,710 cells.
- The builder gives the same 29 key sets over the round-2 stores of the consolidation spike, both
  per-dataset and consolidated.
- **The catalog test keeps the same datasets as the SQL catalog test** for each of the 11 probes
  with a builder form, and the cells are the same (`results/consolidation_filters/filter_language.json`
  against the SQL spike's `filter_language.json`).
- **The null rule.** No store holds a null, so `null_store.py` copied a small store with 14 cell
  types and added `author_cell_type`: the cell type, with every fifth cell null (415 of 2,075).
  For `~(x == v)`, `x != v`, `x == v`, `isna`, `notna`, `~isin`, and `~((x == v) & is_primary_data)`,
  the builder's cells equal pandas over the whole `obs` (`null-rule.json`).
- **Equality with `main`.** On the test stores, for random mapping filters, the bound filter gives
  the rows of `_mask` on every store, and `get_anndata` gives `main`'s result value for value (the
  cell order, every `obs` value and dtype, `var`, `X`, and the normalized layer), per-dataset and
  consolidated. The categories differ in one way: the builder keeps only the labels that the result
  uses, and `main` keeps the store's labels. On the real stores, the one-dataset query from a
  consolidated member gives the same result as the mapping path.

## 7. Measures

The rig is `census2-sdk/tools/bench` of this branch and of the SQL spike. Each run is a new
process. The records hold the elapsed time of the query, the CPU time of the process (user and
system), every request at the zarr store interface (and, for DuckDB, its HTTP log), the payload,
and the peak RSS. In-region: one m6in.4xlarge (16 vCPU, 64 GiB) in the region of the bucket,
Amazon Linux 2023, Python 3.13, anndata 0.13.4, zarr 3.4.2, obstore 0.12.1, pandas 3.1.1,
pyarrow 26.0.1, DuckDB 2.0.0. Median of 3, configurations interleaved in each repeat.

The configurations:

- `main`: the SDK of `main` at the merge point of the consolidation spike, mapping filters, its
  own open (`main_lean`: the same with the lean open).
- `mapping_pd`: this branch's mapping path (the reader of the consolidation spike) over the
  per-dataset stores, lean open.
- `builder_pd`, `builder_cons`: the builder over the per-dataset stores and over the catalog with
  the 5 consolidated stores.
- `builder_ice` and `duckdb`: the builder over the stores of the Iceberg spike's round 2, and the
  DuckDB path over the fragments of the same datasets.

## 8. What the builder can and cannot express, against the SQL spike

The corpus of the validation harness has 50 bound queries with an `obs` filter. All 50 have a
builder form (`harness/filter_language_builder.py`); the SQL spike also expresses all 50, and the
mapping filter 45. One translation changes a meaning: Census 1's `disease_ontology_term_id in
['MONDO:0005109 || MONDO:0005445']` names a joined value, and the builder has no equality on a
multi-valued column, so it becomes `has_all([...])`, which also selects a cell with a third
member. On the 103 datasets the two select the same 12,822 cells. Of the 16 human queries, 15 ran;
the spatial `dataset_slice` names a dataset that the 103-row catalog does not hold, and the label
check refuses it, where SQL returns no cells.

| Kind (the SQL spike's probes) | Builder | Catalog candidates, builder / SQL | Cells, both |
|---|---|---|---|
| compound boolean | `((obs.tissue == 'lung') \| (obs.tissue_general == 'lung')) & (obs.cell_type != 'macrophage')` | 17 / 17 | 1,885,447 |
| IN | `obs.cell_type.isin(['monocyte', 'neutrophil'])` | 22 / 22 | 122,097 |
| NOT IN | `(obs.tissue_general == 'lung') & ~obs.cell_type.isin(['alveolar macrophage', 'type II pneumocyte'])` | 17 / 17 | 1,822,235 |
| nulls | `obs.raw_variance_nnz.isna()` | 103 / 103 | 0 |
| membership, multi-valued disease | `obs.disease.has_any(['COVID-19'])` | 9 / 9 | 637,638 |
| joined value, as Census 1 | `obs.disease.has_all(['COVID-19', 'normal'])` | 0 / 0 | 0 |
| numeric range | `(obs.cell_type == 'neutrophil') & (obs.nnz >= 2000) & (obs.raw_sum < 20000)` | 14 / 14 | 1,077 |
| numeric range only | `obs.nnz >= 8000` | 103 / 103 | 279,441 |
| prefix | `obs.cell_type.str.startswith('CD8')` | 24 / 24 | 427,977 |
| substring, case-insensitive | `obs.cell_type.str.contains('macrophage', case=False, regex=False)` | 36 / 36 | 581,205 |
| regular expression | `obs.cell_type.str.match('CD(4\|8)-positive')` | 27 / 27 | 1,051,329 |
| ontology closure (T cell) | out of scope by decision; a caller passes isin of the descendant terms | – / 46 | – (3,658,513 in SQL) |
| arithmetic | no arithmetic between columns; a caller filters the result in pandas | – / 15 | – (2,047,708 in SQL) |

What SQL has and the builder does not: ontology closure (out of scope by decision; a caller passes
`isin` of the descendant terms), arithmetic between columns (`raw_sum / nnz > 3`), exact equality
of a joined multi-valued value, functions (`lower`, `length`, list functions), and a text form that
other clients run. What the builder has: static types for each column, a refusal of `==` on a
multi-valued column, the label check with suggestions, pandas null semantics, and no engine or
dialect in the contract. The catalog tests agree for every shared probe; both prove nothing for a
numeric term.

## 9. Relation to other work

- **#40** (the read of runs of kept rows as `X` ranges, open): the builder gives the kept rows as
  sorted positions from the start of the read, which is the input #40 needs. The builder does not
  change `_rows`, so a merge of #40 applies to both paths.
- **The Iceberg spike's narrow store read** (`bench.run --narrow`) reads only the columns of the
  filter and of the count, and selects in pandas. The builder is that idea in the SDK, with codes
  instead of strings, the catalog's residuals, and the consolidated reads.
- **The DuckDB spike.** Its fragments answer `obs`-only questions from Parquet with DuckDB's
  late fetch; the builder answers them from the stores. Section 7 compares the two.
- **`main`'s path.** The mapping path stays. `main`'s profile of the full `obs` read (about 1.2 of
  16 cores busy; string arrays, `vlen-utf8` decode on zarr's event-loop thread, and categorical
  validation as the main parts of the GIL time) is the cost that the builder avoids for the filter:
  it reads no string column and builds no pandas object before the filter.

## 10. Open questions

- **The label check.** Raise for an all-unknown term, warn for a near typo, pass otherwise. Is a
  raise right for a release that does not hold a term yet, for example a query copied from another
  release?
- **A null record in the catalog**, if a later store format admits nulls in an indexed column.
- **Exact equality of a joined value.** A `has_exactly([...])` would give Census 1's meaning
  without an `==` on the joined string.
- **A serial form of a filter** for an R front end or a service. The builder has no text form by
  decision; a JSON form of the normalized tree would be one option.
- **The regular expression dialect.** Python's `re` serves both the catalog and the stores here.
  A front end in another language needs a dialect that both sides share.
- **Counting from the catalog.** A filter on counted columns only could count from the catalog's
  `cell_counts` with the same compiled expression, as `count_cells` does for a mapping filter.
- **One round or two.** Two rounds save bytes and decode for a selective filter and cost one more
  round trip for a broad one; a per-dataset store holds each column in one chunk, so the second
  round reads whole chunks anyway.
- **Numeric ranges in the catalog.** A numeric term proves nothing, so `nnz >= 8000` reads all 103
  stores for 58 with a cell.

## 12. Sharp edges

- mypy falls back to `object.__eq__` for a refused `==`, so the refusal needs `@deprecated` and the
  error code `deprecated` (section 2.2). An `__eq__` overload pair needs `# type: ignore[override]`
  on its first `@overload` line and `[overload-overlap]` on that overload's `def` line.
- A dataclass with a custom `__eq__` has no hash; the column classes need none. The tree nodes are
  frozen dataclasses, so equal trees hash alike, and `Expr.__bool__` raises, so the SDK code never
  tests a node for truth.
- `TRUE` and `FALSE` constants carry an organism, so a comparison with `==` fails across
  organisms; `is_const` tests the value.
- `pd.Index(numpy_strings[used])` of an empty selection has another dtype than a selection with
  values, and `union_categoricals` then refuses the parts. Slice an Index of all categories instead.
- `Table.filter` with an expression takes every column; project a mask with Acero instead.
- A script under `spikes/` that imports `bench` needs `PYTHONPATH=.` from `census2-sdk/tools`:
  Python puts the script's directory on the path, not the working directory.
- `get_anndata` of a broad builder filter reads `X` for every kept cell: the new queries that keep
  hundreds of thousands of cells run as counts by donor in the benchmark.
